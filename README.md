# 服务器运维工作台

> A DSH plugin for 1–3 Linux servers: read-only SSH health checks, a triage playbook, and a daily ops report. Install with `dsh plugin add github:shaobingtongzhi/dsh-ops-workbench`.

一个装进 DSH（DeepSeek Harness）的运维面板。它解决的问题很具体：

> 我有 1–3 台云服务器，不知道该盯什么、出问题从哪看、每天该做什么。

- 包名：`dsh-ops-workbench`　·　插件 id：`ops-workbench`　·　许可证：MIT
- 需要 DSH 的 Web 面板（桌面版或 `dsh web` 都行），装完在左侧栏出现「运维工作台」图标

## 它做什么

**健康总览** —— 每台机器一张卡：CPU、内存可用、磁盘、inode、负载、网络、运行时长，配一个结论点（正常 / 有隐患 / 要处理）。看一眼就知道哪台不对劲。

**巡检** —— 一次 SSH 只读采集，跑一段 POSIX `sh` 脚本，回来做判定，产出**带原因和处置建议**的问题清单，不是丢一堆数字给你：

```
🔴 磁盘 / 用到 94%
   为什么算问题：剩不到 6%，日志或数据库再涨一点就写不进去了
   建议动作：先 du -sh /var/log/* 找大头，清掉旧日志；再查 logrotate 是否在跑
```

阈值可改（CPU、内存、Swap、磁盘、inode、每核负载、时间偏差、失败服务数），默认值按「小网站能扛住」定的。

**排障** —— 13 个只读动作，按「出事了先看哪里」的顺序排列：

| 动作 | 什么时候点 |
| --- | --- |
| 失败的服务 | 网站 502、某个功能突然不响应 |
| 最近的错误日志 | 知道出事了但不知道哪一步炸的 |
| 监听的端口 | 服务在跑但外面连不上 |
| 某个进程 | 想确认进程还在、谁在吃资源 |
| 磁盘空间 / 磁盘 IO | 写不进去东西、机器卡 |
| 网络连接 | 怀疑被打、连接数异常 |
| 登录失败记录 | 怀疑被爆破 |
| OOM / 内核杀进程 | 服务莫名消失 |
| 时间同步 | 证书报错、日志时间错乱 |
| Docker / 定时任务 | 容器或 cron 没按预期跑 |
| 最近改动 | 出问题前有人动过什么 |

**每日日报** —— 一句话结论 + 一张总览表 + 需要处理的问题（含怎么处理）+ 明天先做三件事。可复制、可下载 `.md`，适合贴群里或当交接记录。

**该做什么** —— 一页纸的运维常识：每天 3 分钟做什么、每周做什么、每月做什么、出事时的顺序，以及新手最容易忽略的 5 件事。

## 它不做什么（重要）

- **不改你的服务器。** 所有动作都是只读采集，没有重启、没有改配置、没有删文件。
- **不碰你的数据。** 磁盘只统计真实块设备：容器镜像层（`overlay2/…/merged`）、`tmpfs`、snap 的 loop 分区都不计入 —— 它们要么和宿主机同一块盘，要么永远 100% 满，算进来只会误报。卡片上**每个挂载点单独一行**（根分区 `/` 在最前，数据盘跟在后面），各自一根进度条，超阈值那行才变色。

故意这样的：第一版要让你先「看清楚」，手滑代价为零。等你看熟了流程，我们再在「确认后执行 + 留痕」的前提下加动作。

## 安装

三种方式，任选一种。

**1. 从 GitHub 装（给别人的用法）**

在 DSH 里打开 **插件 → 添加插件**，填 Git 地址：

```
github:shaobingtongzhi/dsh-ops-workbench
```

或者用命令行等价的写法：

```bash
dsh plugin --profile web add github:shaobingtongzhi/dsh-ops-workbench
```

装完在「插件」页把它打开，刷新页面，左侧栏最下方出现「运维工作台」图标。

> pnpm 如果提示 `ssh2` 的依赖有待批准的构建脚本，可以直接跳过：`cpu-features` 只是加速项，不编译照样能连。

**2. 从本地目录装（开发时用）**

```
plugin_manager  action=install_bundle  target=/绝对路径/ops-workbench
```

**3. 从 tarball 装**

```bash
npm pack            # 得到 dsh-ops-workbench-1.0.0.tgz
dsh plugin --profile web add ./dsh-ops-workbench-1.0.0.tgz
```

依赖 `ssh2` 声明在 `package.json` 里，安装时由 pnpm 拉取；本仓库的 `.gitignore` 排除了 `node_modules/`，所以克隆下来开发时先跑一次 `pnpm install`（或直接用本机已装好的 `node_modules/`）。

## 用起来

1. 进「主机」→ 添加主机：地址、端口、用户名、密码。
2. 点「测连接」确认能上去（会显示 `whoami@hostname` 和后端指纹信息）。
3. 回「总览」→「全部巡检一次」。
4. 看「巡检」里的问题清单，一条条处理。
5. 每天收工前点一次「生成今天的日报」。

## 自动巡检与日报

装上就开始跑，不需要开着页面 —— 定时器在宿主进程里，只做只读采集：

| 项 | 默认 | 在哪儿改 |
| --- | --- | --- |
| 自动巡检 | 每 15 分钟，对全部主机 | 「巡检」→「定时任务」 |
| 每日日报 | 每天 09:00（本机时间）生成 | 同上 |
| 趋势数据 | 每台保留最近 480 次采样（约 5 天） | 固定 |

- 巡检结果写进同一份状态，页面每 20 秒同步一次（标签页切回来时立即同步），所以自动巡检跑完不需要手动刷新。
- 日报落盘到 `~/.dsh/ops-workbench/reports/YYYY-MM-DD.md`，「日报」页可以回看历史；同一天只生成一份。
- 手动点过「巡检所有主机」也算跑过一次，不会让定时器紧接着再连一遍。
- 宿主的 30 秒心跳负责判断「到点没」，所以电脑睡眠唤醒后不会漏掉太多次，最多补跑一次。
- **连不上不等于服务器挂了**：刚开机 / 刚唤醒 / VPN 还没连上时，一轮巡检可能一台都连不上。这种情况显示成灰色「连不上」并给出原因，不会算进红色「要处理」，也不会写进趋势曲线（没有数据就不画点）。
- 一整轮全部失败时，宿主会在 1、2、3 分钟后各自动重试一次；只要有一台通了就停止重试。每次尝试都记在 `state.json` 的 `attemptLog` 里（最近 20 条），方便事后回答「刚才为什么全是离线」。

## 改完代码怎么确认生效

DSH 的两半加载方式不同，所以「要不要重启」的答案也不同：

| 改了什么 | 怎么生效 | 要做什么 |
| --- | --- | --- |
| `client.js`（界面） | 宿主每隔 500ms 用文件的 mtime/ctime/大小算出版本号，一变就通过 `/plugins/events`（SSE）推给页面，页面就地替换这个插件并重新挂载 | **什么都不用做**，一两秒内自己换上来 |
| `index.js` 与 `lib/*.js`（后台） | 已安装的包在进程内不会换成新的模块（官方文档：替换已安装的包需要重启才能加载新一代模块） | 把插件关掉再打开即可，等价于重启那一半；不必退出 DSH |
| 数据 `state.json` | 每次请求现读 | 无关 |

面板顶部副标题有一行会显示**页面代码 XX:XX:XX 载入**——这个时间是 bundle 被浏览器执行的时刻，热更新成功会重新执行整份文件，所以时间一跳就说明页面已经是新代码。如果改完界面这行时间没变，点右上角**「重载页面」**（等价于 F5；桌面端菜单里没有「重新加载页面」这一项，面板自带了这个入口）。

## 关于密码（请读）

主机的密码以**明文**存在本机：

```
~/.dsh/ops-workbench/state.json   （文件权限 0600）
```

为什么这么干：把密码塞进系统凭据库需要一个「引用谁的 key」的语义，DSH 的 `credentials` 服务是绑在模型 provider 上的，用在服务器密码上会变成套娃。文件权限 0600 + 只存本机，是这个规模下更实在的选择。

不放心的话，改用密钥登录：主机编辑里选「私钥文件」，填本机私钥路径或直接粘贴私钥内容。密码就完全不用落盘。

## 传输层

- 主路径：`ssh2`（纯 JS，`package.json` 的 `dependencies`）。原因 —— 很多机器上没有 `sshpass`/`plink`，`ssh.exe` 没法在非交互场景喂密码，而你的服务器只有用户名密码。
- 兜底：`ssh2` 加载失败时自动退回系统 `ssh`（只能密钥登录，`BatchMode=yes`），页面上会说明当前通道。
- `cpu-features` 是 ssh2 的可选加速依赖，没编译也能跑，只是密钥交换慢一点。

## 判定标准（默认）

| 指标 | 提示 | 严重 |
| --- | --- | --- |
| CPU 使用率 | 85% | 95% |
| 内存可用 | 低于 15% | 低于 8% |
| Swap 使用率 | 40% | 75% |
| 磁盘使用率 | 85% | 93% |
| inode 使用率 | 85% | 95% |
| 每核负载 | 1.0 | 2.0 |
| 时间偏差 | 60 秒 | 300 秒 |
| 失败服务数 | 1 个 | 3 个 |

每个阈值都配了一句「为什么这算问题」，不是干巴巴一个数字。

## 结构

```
ops-workbench/
  package.json        包清单：dsh.bundle.patch、dsh.client、exports、files
  cordis.patch.yml    把插件插进 profile 的补丁
  index.js            宿主半边：12 个 /ops/api/* 路由，CSRF 用 nonce 头
  lib/ssh.js          SSH 传输（ssh2 主路径 + 系统 ssh 兜底），错误话术中文化
  lib/probe.js        采集脚本、分段解析、阈值判定
  lib/diag.js         13 个只读排障动作
  lib/report.js       日报生成
  lib/store.js        状态存取（~/.dsh/ops-workbench/state.json）
  client.js           面板 UI（总览/主机/巡检/排障/日报/指南）
  locale/*.json       插件页展示用文案（中/英）
  icon.svg            侧栏与插件页图标
```

## 权限与兼容性（装之前请看）

| 项 | 说明 |
| --- | --- |
| 网络 | 只连你在面板里填的服务器（SSH，默认 22 端口）；不连任何第三方服务 |
| 读取 | 远端只跑一段只读的 POSIX `sh`：`/proc`、`df`、`ss`、`systemctl status`、`docker ps`、`journalctl`、`cron` 等 |
| 写入 | 只写本机 `~/.dsh/ops-workbench/`（状态、日报、客户端日志）；**不写远端任何文件** |
| 凭据 | 密码明文存本机 `state.json`（0600）；不上传、不打日志、不经模型上下文 |
| 依赖 | `ssh2`（纯 JS）；`cpu-features` 是它的可选加速依赖，没编译也能跑 |
| 运行环境 | DSH 桌面版或 `dsh web` 的 Web 面板；Node.js >= 22.6；Windows / macOS / Linux 宿主都可 |
| DSH 目标版本 | 在 0.2.2 系列上开发与验证（插件用宿主公布的 `webServer` / `slots` / `uiWorkspace` 接口） |
| 能力分类 | 开发与运维 |
